# HTTPS、TLS 证书和代理

## 结论先行

1. 浏览器开发工具能显示 HTTPS 请求体中的密码，不等于网络上明文传输。
2. HTTPS 使用 TLS 保护连接的机密性、完整性，并在正确校验条件下验证服务端身份；它不代替业务授权、密码存储和日志保护。
3. 证书需要匹配所访问的名称、有效期与可信证书链，不能用“忽略错误”作为正式方案。
4. 反向代理终止 TLS 后，到应用的下一段连接是否加密必须单独判断。

## 业务场景：浏览器看见了密码

模拟“青禾制造”的员工通过 HTTPS 登录查询网站，开发者工具中 Request Body 显示用户输入的口令。有人要求前端先做一次普通 SHA-256 哈希，再改用 HTTP。这个判断混淆了浏览器本地处理数据与网络旁观者所能看到的数据。

浏览器是发送端，在加密前当然需要处理请求内容；服务器是接收端，解密后也要处理内容。TLS 保护的是两端之间的传输，不保证两端机器本身没有恶意程序，也不会自动阻止应用把口令写进日志。

## 核心概念：连接、证书与终点

**TLS** 是建立受保护连接的协议。通常 HTTPS 将 HTTP 放在 TLS 连接上。握手过程协商参数、验证服务端证书并建立会话密钥，之后请求路径、请求头和请求体等 HTTP 内容在连接上传输时受加密保护。某些网络元数据仍可能可见，不能据此认为通信完全匿名。

**证书** 将服务身份与公钥等信息关联，并通过可信签发链等机制帮助客户端验证。校验不只是“文件存在”，还包括目标名称、信任链、有效期等。内网域名也需要客户端能够信任的合适证书体系；自建 CA（证书颁发机构）需要管理信任分发和更新。

**反向代理** 是服务端的入口，接收客户端请求后转发到应用。代理可负责 TLS、路由和访问限制，但不能替代应用对“该员工能看哪笔订单”的判断。

## 工作原理与边界

```text
浏览器 == TLS 连接 A ==> 反向代理 -- 连接 B --> 应用 -- 连接 C --> 数据库
```

连接 A 加密不意味着 B、C 自动加密。B 如果经过不可信网络，通常也应配置受保护连接；如果是同一主机的受限本地通信，则需要结合隔离、监听地址、权限和威胁模型评估。评审应逐段记录，不要把地址栏锁图标理解为全链路证明。

| 要保护的问题 | HTTPS 是否足够 | 还需要什么 |
|---|---|---|
| 网络旁观者读取 HTTP 内容 | 在正确配置与校验下提供保护 | 避免证书绕过和不安全跳转 |
| 数据库口令验证数据泄露 | 不足 | 合适的带盐慢速密码哈希方案与访问控制 |
| 其他部门越权查询 | 不足 | 服务端授权与数据范围校验 |
| 日志保存完整口令 | 不足 | 源头不记录、脱敏与日志访问控制 |

前端普通哈希不能代替 TLS，也不等于服务器适当的密码存储。若服务器把客户端哈希直接当登录凭据，它可能成为可直接重放的等价秘密。不要自行发明口令协议，应使用经审查的认证方案。

## 企业案例：入口加密后的遗漏

模拟系统的代理启用 HTTPS，但应用直接监听在所有网络接口上，员工可绕过入口访问 HTTP 端口。错误思路是只对外展示 HTTPS 链接。建议明确入口与后端的网络访问边界，限制应用端口来源，核查代理转发的身份相关头部是否能被外部伪造。

验证时检查正式访问地址是否全程使用正确 HTTPS，证书错误是否被正常拒绝，后端端口能否被非授权来源访问。随后检查登录日志是否包含口令、会话是否安全处理、服务端是否对订单数据授权。测试使用虚构账号，不把真实口令粘到报告。

这里不要求 PM 编写 TLS 算法或背诵全部密码套件；需要能标出加密终点、提出配置问题并核验相关证据。具体配置随服务器和版本变化，应以实际组件的官方文档为准。

## AI 易忽视的问题

- 为了调试永久关闭证书校验，掩盖域名或证书链错误。
- 只配置入口证书，却未限制直接访问应用端口。
- 把请求体、URL 参数或异常上下文整体写入日志。
- 把客户端哈希描述成替代 HTTPS 的通用方案。
- 忘记证书续期、内部 CA 信任部署及更新责任。

## PM 评审问题

1. TLS 在哪里终止，每段后续连接如何保护？
2. 客户端如何校验证书，是否存在跳过校验的代码？
3. 证书名称与正式域名是否匹配，谁负责到期更新？
4. 应用原始端口是否允许绕开代理访问？
5. 密码、会话和敏感字段会不会进入 URL、日志或错误报告？
6. 服务端如何保存密码验证数据并限制登录与数据访问？

## 微实践：给访问链路上色
