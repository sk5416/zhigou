# REST API 与接口契约

## 结论先行

1. 接口契约既定义正常返回，也定义输入约束、身份权限、错误、分页和兼容方式。
2. JSON 样例只能说明一种数据形状，不能代替完整字段规则与失败行为。
3. REST 是理解资源和交互约束的架构思路，不是“URL 有复数名词就完成了设计”。
4. 契约写清调用者可依赖什么，并用测试确认实现遵守，才有稳定协作基础。

## 业务场景：能调通，却无法稳定接入

模拟订单接口首批返回十行，调用方以为已经取完；后来数据超过默认页长便漏数。另一个字段 `amount` 有时是数字、有时是文本。两边都说“接口能用”，但没有共同理解分页与类型，这才是需要修复的边界。

## 核心概念：资源、表示与约定

资源是接口讨论的对象，例如订单；路径用于定位对象，方法表达操作语义，表示承载对象的可交换数据。是否采用某种路径风格应结合现有系统，不为追求形式随意破坏已用接口。

下面是虚构契约的一部分，不代表任何 ERP 产品行为：

| 项目 | 约定示例 |
|---|---|
| 读取入口 | GET `/api/orders`，要求已验证身份 |
| 输入 | `pageSize` 为 1～100 的整数，默认 20 |
| 数据范围 | 服务端按身份过滤，不能靠调用者自报部门 |
| 返回 | `items` 数组；金额示例用十进制文本并标明币种 |
| 后续页 | `nextCursor`，无后续时明确为空 |
| 错误 | 稳定错误代码、可理解说明、请求关联号 |

该表没有规定所有系统都应如此；重要的是实际双方对字段和行为达成一致，并注明未覆盖的事项。

## 工作原理：将“样例”补成可依赖规则

逐字段说明类型、是否必填、是否可为 null、空字符串与缺失是否不同、时间格式及时区、金额精度与枚举范围。例如“缺失不修改、null 清空”只有契约明确并实现验证时才成立，不能由 AI 自行推断。

分页要有稳定排序和边界规则。页码在数据变化时可能重复或漏读；游标也不是天然快照，需要说明它代表什么、何时失效以及调用方如何继续。批量动作应按业务标识返回逐项结果，不把整批 HTTP 成功当每行成功。

错误信息既要支持调用方区分输入问题、身份失效、权限不足、冲突和临时故障，也不能泄露口令、内部查询或堆栈。业务错误代码应比易改文案更适合作程序判断依据。

兼容不是简单增加版本号。新增必填输入、改变字段类型、删除值或改变原语义，都可能影响调用者。新增可选字段也要检查调用方是否容忍未知字段，不能绝对承诺无风险。

## 企业案例：修复漏页与金额歧义

模拟双方补充后续游标规则、固定排序、金额类型和币种，并用大于两页的虚构订单测试。验证空结果、最后一页、无效游标、权限不足及数据变化。错误方案是让前端把收到的数据当全部，或把无法解析的金额默认为零；这会隐藏差异。

将期望行为写成契约测试，例如确认每页不超过上限、字段类型符合约定、未授权订单不会出现在任何页。契约测试不能代替真实业务对账，但能在变更时更早发现不兼容。

## AI 易忽视的问题

- 只提供成功 JSON，不说明空值、失败和分页终点。
- 用隐藏字段或前端过滤承担权限。
- 根据错误文案匹配流程，文案修改后调用失效。
- 修改接口时只测新客户端，不核查现有使用者。

## PM 评审问题

1. 哪些调用者依赖此接口，权限和数据范围是什么？
2. 必填、类型、空值、时间和金额口径是否逐项定义？
3. 如何取完全部结果，排序与分页在变动数据下有什么限制？
4. 部分成功和不同错误如何被调用方识别？
5. 什么变化可能破坏旧调用者，如何验证与通知？
6. 文档、实现和测试是否描述同一版本的契约？

## 微实践：评审一份不完整样例

模拟样例只有 `{"items":[{"id":"O1","amount":"100.00"}]}`。补问币种、精度、授权范围、空结果、下一页、错误、版本和稳定编号。选择两项写成验证输入及预期输出，体会契约如何变成验收依据。
