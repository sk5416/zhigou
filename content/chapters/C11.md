# HTTP 请求、响应与浏览器机制

## 结论先行

1. HTTP 请求包含动作、目标及元数据，响应包含状态及内容；看懂一次交互有助于区分页面、接口与数据问题。
2. 成功状态码不等于业务结果或权限正确，失败状态也要结合响应来源和契约解释。
3. Cookie 是浏览器存储、按规则发送的数据机制；Session 是应用维持会话状态的方式，二者有关但不同义。
4. 开发工具看到的是端点处理的数据，排错材料仍需脱敏，不复制完整口令或令牌。

## 业务场景：页面提示失败，接口却返回 200

模拟订单页收到响应 `{"success":false,"message":"无数据权限"}`，HTTP 状态为 200。先确认这是不是接口约定，再检查前端是否只按状态码显示成功。该设计并非仅凭一个状态就能评判全部对错，但若调用者对业务失败没有一致处理，会造成误报。评审应要求清楚、统一且可测试的成功和失败契约。

## 核心概念：请求各部分放什么

以下是虚构接口的 HTTP/1.1 示意，不是真实企业服务。

```http
GET /api/orders?page=1&pageSize=20 HTTP/1.1
Host: query.example.test
Accept: application/json
```

方法表示动作语义，路径与查询参数定位目标及条件；Header（请求头）承载内容类型、认证等元信息；Body（请求体）按接口约定承载内容。GET 常用于读取，POST 常用于提交处理，不应仅按“有没有参数”选择方法。真实 HTTP/2、HTTP/3 的传输表示不同，本章示意用于读懂共享语义。

响应状态区分成功、重定向、客户端问题和服务端问题等类别。JSON 是常见数据表示，不是授权证明或正确性保证。解析时仍需核对字段、类型、空值及业务含义。

## 工作原理：浏览器不是透明电线

浏览器会处理缓存、重定向、Cookie 和安全策略。页面能从缓存显示，但本次数据请求可能失败；请求也可能被重定向到登录页面，最终得到 HTML，而前端原本期待 JSON。网络面板应检查实际 URL、重定向链、状态、响应类型和内容，而非只看最后一个绿色数字。

Cookie 可以承载不透明会话标识，由服务端用它关联会话；也可用于其他用途。Session 失效、Cookie 未按预期发送、服务端拒绝身份，是需要分别定位的情况。Cookie 的作用范围和保护属性、跨站请求风险，会在安全章节进一步展开，不用“Cookie 都不安全”或“令牌自动安全”概括。

| 观察 | 可提出的下一问 |
|---|---|
| 400 | 哪项输入违反了约定，错误是否定位到字段？ |
| 401 | 是否缺少或失效了所需身份凭据？ |
| 403 | 哪项访问被拒绝，是否符合授权规则？ |
| 5xx | 错误来自代理还是应用，如何关联日志？ |

状态含义要与实际契约和来源一起核对，不能从某个错误反推数据库一定怎样。

## 企业案例：登录页被当作订单数据

模拟会话过期后，订单请求被重定向，最后返回登录页 HTML。AI 只看到最终状态 200，判断“接口正常”，前端却报 JSON 解析错误。建议核对重定向与内容类型，设计明确的身份失效响应和页面反馈，再验证未登录、过期与正常身份。

排错记录包括脱敏 URL、方法、时间、请求关联编号、状态与响应类型。不把开发工具的完整请求一键分享，因为 Cookie、认证头和正文可能含秘密。若使用 HTTPS，请求体本地可见不说明链路明文，需参考下一章。

## AI 易忽视的问题

- 将空列表、业务失败、未登录和服务不可用统一显示为“暂无数据”。
- 假定所有响应都是 JSON，未处理登录跳转或代理错误页。
- 把请求中的部门参数当成可信授权依据。
- 将完整请求头和正文写进普通日志。

## PM 评审问题

1. 哪种响应才算业务成功，页面如何区分失败类型？
2. 响应来自哪个组件，是否发生重定向？
3. 约定的字段、类型与内容类型是否一致？
4. 会话过期和权限不足分别怎样表现？
5. 排错材料如何帮助定位又避免泄露凭据？

## 微实践：阅读模拟响应

比较“200 + 订单 JSON”“200 + 登录 HTML”“403 + 错误 JSON”。分别写出传输层结果、预期内容是否满足、下一步证据。不要把“200”自动翻译为订单已授权返回，也不要用反复刷新替代会话诊断。
