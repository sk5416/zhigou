# 附录 B｜技术选型评审清单

适用于模拟部门工具、员工查询和企业接口集成的方案比较。清单帮助约束讨论，不预设某个框架永远最佳。

## 先说问题与约束

- 用户是谁、同时使用多少人、多久使用一次？个人离线工具不应自动套用多人服务架构。
- 数据是否敏感，是否跨部门共享，需要怎样的身份与数据权限？
- 在哪里运行，网络、终端、操作系统和现有部署能力有哪些限制？
- 谁维护、能投入多少时间、预期使用几年、离职后谁接手？
- 哪些功能明确不做，哪些规模或性能要求尚未有证据？

## 要求至少两个可比较方案

用同一组需求比较简单脚本、单机应用、低代码或 Web 系统等适用选项。比较开发与运维成本、数据保护、测试能力、依赖成熟度、迁移和交接，不以流行度替代依据。

| 比较维度 | 需要的具体信息 |
|---|---|
| 功能适配 | 需要定制的范围，平台限制及绕行代价 |
| 可靠性 | 故障后能否重试、恢复、对账，有无单点 |
| 可维护性 | 维护者已有能力、依赖更新频率、文档与测试 |
| 成本 | 初始开发、许可、服务器、备份、日常维护与退出 |
| 安全 | 身份、授权、密钥、日志、依赖与数据边界 |
| 可替换性 | 数据能否导出，平台锁定影响，迁移路径 |

## 审查额外组件的理由

引入缓存、队列、微服务或集群前，追问：哪个已测量的问题需要它？不用会出现什么可观察后果？引入后谁负责更新、监控、恢复和排错？如果只是“以后可能用到”，通常先记录扩展条件，比立即采购复杂度更可控。

也不能一味求少：需要多人权限、持续运行与审计的服务，不能因为用户少就共用管理员口令。合理简化应保留与实际风险对应的控制。

## 决策记录的最小结构

记录日期、背景、备选方案、选择理由、代价、未验证假设和重新评估条件。例如“单机工具已满足当前单人使用；当多人共享和权限要求出现时重新评估 Web 方案”。要求 AI 给出验证计划，不能只输出排行榜。
