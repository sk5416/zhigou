# 同步、异步、定时任务与消息队列

## 结论先行

1. 同步关注调用方等待结果，异步可把开始与完成分开；异步不保证并行、持久化或成功。
2. 定时决定何时触发，任务状态决定正在发生什么，两者需要分别设计。
3. 进程内后台任务可能随进程退出丢失；需要可靠完成时，必须说明保存、恢复与确认边界。
4. 队列能解耦工作与处理者，也会引入重复、积压、顺序和运维问题，不能无条件添加。

## 业务场景：页面已返回，夜间任务却消失了

模拟员工提交一份耗时导出，页面立即提示“完成”，程序只在内存启动后台函数。服务器重启后没有文件，也没有可查询状态。更合理的反馈是“已受理”并提供任务标识，只有确认产物存在且可访问时才报告完成。

## 核心概念：等待、并发与调度

同步调用通常等待返回再继续处理；异步调用可在结果未完成时将控制权交回，完成结果另行取得。并发意味着任务执行时间段可能交错，真正并行则涉及同时执行的资源条件，二者不能混为一谈。

Python 的 `async`/`await` 可用于理解协作等待，以下 `client` 是模拟接口，不是任何真实厂商 SDK：

```python
async def read_one(client, code):
    return await client.get_material(code)
```

`await` 不意味着创建新服务器或 CPU 密集工作自动变快；仅调用异步函数也不能假设任务已被调度并完成。具体执行依赖运行框架和调用方式，本章不要求掌握事件循环内部实现。

## 工作原理：把任务当有生命周期的对象

一种模拟任务状态为：待处理、处理中、已完成、已失败、结果待核查。任务标识、输入摘要、进度、结果位置和错误需要相应保存。长任务应能让用户查询状态，重复点击应考虑防重。

| 方案 | 适用条件示例 | 需要补查 |
|---|---|---|
| 同步处理 | 轻量且等待可接受 | 超时、重复点击和错误反馈 |
| 进程内后台 | 可重做、丢失影响低的受控工作 | 进程退出、取消及资源限制 |
| 持久任务/队列 | 需要可恢复、解耦或削峰 | 保存确认、重试、防重与积压监测 |
| 定时任务 | 周期核对或批量窗口 | 重叠执行、漏触发、时区与补跑 |

队列通常只能帮助组织交付与确认，并不自动证明业务恰好处理一次。消费者写入成功但确认丢失时，消息可能重投，仍需幂等。处理失败的消息也要有上限、隔离或人工处置路径，不无限循环。

## 企业案例：按影响选择必要复杂度

模拟单人本机生成可随时重做的小报表，有限等待或简单后台机制可能足够。另一任务要批量写入 ERP，进程重启后必须知道哪些已执行，就需要持久状态、稳定业务标识、结果核查和受控重试；是否引入独立队列仍需比较现有能力与维护成本。

验证应覆盖提交后重启、处理中断、重复投递、同一任务重复提交、失败后重做及产物不可用。用户取消等待不证明外部业务动作已取消；如果远端可能已经处理，要保留结果核查能力。

## AI 易忽视的问题

- 将 HTTP 已返回等同后台业务完成。
- 把进程内线程或协程当成持久队列。
- 每次定时触发都启动新任务，未防止与上一次重叠。
- 引入队列却不定义确认、重试和积压处置。

## PM 评审问题

1. 用户拿到的是已受理还是已完成，如何确认？
2. 任务和结果在哪里保存，重启后怎样接续？
3. 超时、取消、失败与结果未知分别如何表示？
4. 重复执行会不会重复写入，谁负责防重？
5. 调度重叠、时区和漏触发怎样处理？
6. 选择队列的具体收益和维护责任是什么？

## 微实践：画一个任务状态流

模拟批量导出先受理、后执行，处理中服务器重启。画出用户能看到的状态、存储与恢复动作，再加入“文件已生成但通知丢失”的反例。说明为什么只看通知不够，以及如何避免重复生成或泄露下载结果。
