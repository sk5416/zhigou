# 对象、模块、分层与项目目录

## 结论先行

1. 类描述一类对象的数据与行为，对象实例保存具体状态；类名多不代表结构好。
2. 模块与目录帮助组织职责，但文件放在 `service` 下不证明它没有混入其他责任。
3. 接口入口、业务规则和数据访问分开，有助于定位改动与测试；层数应服务实际需要。
4. 阅读项目先追踪一条业务动作的调用链，再决定改哪里，不按文件大小盲目重构。

## 业务场景：导入规则究竟藏在哪

模拟“数量必须大于零”的规则同时出现在网页、接口和导入脚本，三处实现略有不同。新增批量入口后绕开校验。你需要能沿请求追到可信业务规则和写入位置，而不只是让 AI 在搜索到的第一个文件改一行。

## 核心概念：对象状态与模块职责

类可以把有关数据与操作组织在一起，创建的对象实例代表某个具体批次或业务对象。模块提供一组相关定义，导入关系体现代码依赖。对象不等于数据库表，一张表也不要求对应固定数量的类。

下面是 Python 的错误状态示例，不是推荐实现：

```python
class ImportSummary:
    # 可变列表属于类，实例可能共享它
    rejected = []
```

若两个批次都使用这个列表，上一批错误可能混进下一批。需要按预期把每批状态放在实例中，例如在 `__init__` 里创建 `self.rejected = []`。但将状态改为实例也不自动解决多个进程或并发写入问题，仍需看实际生命周期。

## 工作原理：从入口走到数据

```text
页面或接口入口 → 输入解析与身份边界 → 业务规则 → 数据访问 → 数据库
```

这是一种职责划分，不要求每个箭头都成为服务、类或文件。简单工具可少一些结构；业务复用和测试需要明确时，再提取共同规则。

| 位置 | 应回答的问题 | 典型混杂 |
|---|---|---|
| 入口/路由 | 从哪里进来，参数和身份如何处理 | 在每个入口复制不同规则 |
| 业务模块 | 本动作允许什么，失败怎样表示 | 依赖网页控件判断核心规则 |
| 数据访问 | 如何查询、写入并处理事务 | 无限制拼接输入到查询 |
| 配置与运行入口 | 环境参数、组件如何装配 | 在业务函数写死真实凭据 |

分层不是规定“只能某层授权”。身份、业务权限与数据库最小权限有各自位置，关键是可信服务端必须执行相应控制，各入口不能绕开。评审时要求 AI 指明实际校验点，而不是仅展示漂亮目录树。

## 企业案例：新增入口也遵守同一规则

模拟修复将核心数量规则放入可复用业务函数，页面校验用于及时反馈，接口和批量入口都调用服务端规则；数据库仍维护必要约束。验证同一组虚构边界记录从不同入口进入，结果应与统一契约一致。

错误修复是只移动文件或给每个字段新增一层类，规则仍然复制三份。也不要为了抽象统一完全不同的业务：采购收货和退货允许的数量条件可能不同，必须先确认语义。

## AI 易忽视的问题

- 为每个简单函数增加多层包装，却不能说明替换或测试收益。
- 使用全局或共享可变状态记录用户/批次数据。
- 改了某个页面路径，遗漏脚本或其他接口调用者。
- 移动文件后未检查导入关系、构建和运行入口。

## PM 评审问题

1. 一次导入实际经过哪些文件和调用？
2. 核心规则在哪里，其他入口会不会绕过？
3. 对象或全局状态由谁创建、何时清理、是否共享？
4. 这层抽象解决什么复用、测试或替换需求？
5. 改动会影响哪些调用者，如何证明没有遗漏？

## 微实践：给目录加上职责

模拟目录有 `api.py`、`rules.py`、`storage.py`、`settings.py`。为“数量校验、读取数据库、配置地址、解析请求”各找合理位置，再说明它们如何连接。若实际代码不符合文件名，要以真实调用为准，要求 AI 给出定位证据。
