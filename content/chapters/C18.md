# 分支、合并、冲突与回退

## 结论先行

1. 分支帮助组织独立变化，不是数据库、密钥和运行环境的自动隔离。
2. 合并冲突意味着需要决定如何整合不同修改，不是随意选择“当前”或“传入”即可。
3. 丢弃未提交修改、移动历史指向、用新提交撤销旧改动，影响对象不同。
4. 回退代码不等于撤销数据库迁移或外部业务写入，必须核查兼容与副作用。

## 业务场景：两个修复改了同一个条件

模拟分支甲修复空值校验，分支乙增加退款场景。它们修改同一段数量判断，合并产生冲突。若 AI 为消除标记直接保留其中一边，可能丢失另一项业务规则。真正需要的是重新确认业务语义，并组合相应反例测试。

## 核心概念：分支与整合

分支为一条工作线提供可移动的历史名称，提交可先在分支上独立演进，再整合到其他工作线。工作区未提交内容是否可随切换保留，要看具体状态与冲突风险，不能把切换分支当保存全部工作的方法。

Git 能自动合并许多文本变化，但即使没有文本冲突，也可能有语义冲突：例如一处改字段类型，另一处仍按旧类型计算。合并成功仍需要测试调用链和契约。

## 工作原理：先确定要撤销什么

| 目标 | 需要理解的区别 |
|---|---|
| 撤销未提交文件改动 | 可能丢失尚未记录的工作，先保护与核对范围 |
| 调整本地提交组织 | 涉及历史与暂存/工作区影响，不能套用同一参数 |
| 撤销已分享的提交效果 | 可评估用新提交表达反向改动，保持可审阅历史 |
| 恢复已上线系统 | 还需处理产物、配置、数据库及业务副作用 |

`revert` 通常通过新提交记录对旧提交效果的撤销，也可能发生冲突，需要核对结果。`reset` 可改变引用并按模式影响暂存或工作区，某些方式会丢弃修改；它不是默认的“修复按钮”。本章不要求背全部参数，执行前必须弄清目标、当前状态和恢复措施。

共享历史是否重写，需要结合协作约定与影响范围，不能为了让日志漂亮擅自强推。个人分支也应保护尚未提交的成果和重要基线。

## 企业案例：无冲突合并也能破坏业务

模拟甲把金额字段改为十进制文本，乙在另一文件保留按数值直接相加。Git 未报文本冲突，但运行会出现错误。建议检查关联调用者并用虚构金额、空值和错误格式回归，再记录解决理由。

若新版程序已改数据库结构，回到旧代码前核对旧程序能否读取当前结构。远端已经创建的物料不会随代码回退自动删除，必须另行查询、对账或业务补偿。

## AI 易忽视的问题

- 按文件新旧或行数选择冲突结果，不理解业务规则。
- 用“合并无冲突”替代回归测试。
- 未说明影响便执行丢弃工作或重写共享历史的操作。
- 只回退代码，忽略配置、数据库与外部动作。

## PM 评审问题

1. 当前分支、已有修改和待整合范围是什么？
2. 冲突两边分别想解决什么，哪些规则都要保留？
3. 自动合并后还有哪些调用者和契约要验证？
4. 我们要撤销工作区、提交效果，还是运行版本？
5. 该动作是否影响其他维护者及未提交成果？
6. 数据与外部副作用是否支持同一回退方案？

## 微实践：设计一次安全的撤销说明

模拟一个已分享的错误规则提交，后面还有正确的文案修改。要求 AI 提供变更目标、保留项、拟采用方式、差异与测试，而非直接“全部恢复昨天”。说明为什么精确撤销比按日期覆盖目录更容易核验。
