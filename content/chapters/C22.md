# 设计可靠的业务表

## 结论先行

1. 类型、必填、默认值和约束必须表达业务含义，不能只满足页面保存成功。
2. 金额要确定币种、精度与舍入规则；金额、编码、时间都不能靠显示外观判断类型。
3. 软删除、状态和审计字段属于生命周期设计，增加一个标记不会自动解决查询、唯一性和权限问题。
4. 数据库结构应约束可表达的不变量；状态迁移、权限和跨服务规则仍需应用层控制。

## 业务场景：空金额被默认成零

模拟财务流水导入，AI给所有字段补默认值：金额缺失补0，币种缺失补CNY，审批状态默认APPROVED。导入率提高，却把未知金额认作真实零、未审批记录认作已通过。默认值会生成业务事实，必须有依据；对不确定数据应明确拒绝或保留待确认，而非替业务作决定。

## 核心概念：字段表达的是契约

编码如0012应按编码处理，不能转成数值丢前导零。金额可用适当定点小数，或在固定币种和精度约定下用整数最小单位；二进制浮点不适合直接承担精确财务金额等值规则。币种不同最小单位可能不同，不能假定所有货币都两位。

NULL表示缺失或未知，不自动等于0、空串或“未审批”。NOT NULL只限制空值，未必排除空串。创建时间、业务发生时间与修改时间目的不同，要约定时区、来源与时钟可信程度。

## 工作原理：从字段到生命周期

以下SQLite练习仅模拟一种币种、整数分、允许零金额的付款草稿，不是完整会计模型。应用需先完成类型解析和鉴权；SQLite动态类型行为不能泛化为其他数据库。

```sql
CREATE TABLE payment (
  id INTEGER PRIMARY KEY,
  request_no TEXT NOT NULL UNIQUE,
  amount_cents INTEGER NOT NULL
    CHECK(typeof(amount_cents) = 'integer' AND amount_cents >= 0),
  currency TEXT NOT NULL CHECK(currency = 'CNY'),
  status TEXT NOT NULL CHECK(status IN ('DRAFT','APPROVED','CANCELLED')),
  created_by TEXT NOT NULL,
  created_at TEXT NOT NULL,
  version INTEGER NOT NULL DEFAULT 1,
  deleted_at TEXT
);
```

CHECK约束限制可存状态集合，不保证从DRAFT变为APPROVED已获授权；还要检查当前状态、操作者和并发版本。UNIQUE限制request_no，但未自动阻止空串或空白编码，清洗与更严的约束需要额外设计。created_by也不能直接相信客户端自报。

| 决策 | 需要明确的规则 | 常见遗漏 |
|---|---|---|
| 默认值 | 哪种省略代表合法业务值 | 用0掩盖输入缺失 |
| 状态 | 允许的值及允许的迁移 | 任何调用者都能写APPROVED |
| 软删除 | 读取、关联、唯一键与恢复 | 只在列表页隐藏 |
| 审计字段 | 可信操作者、时间与来源 | 覆盖旧值后无法追溯 |

软删除通常保留行并标记失效时间。它不等于访问控制，查询、导出、统计和关联都应遵守可见规则。本例request_no终身唯一，即使软删除也不允许复用；如需“仅有效记录唯一”，应按数据库方言设计并验证唯一索引与恢复冲突，不能只在页面先查。物理删除与保留期限是另一项明确决策。

## 企业案例：补约束前先处理旧数据

模拟准备给已有付款表增加request_no唯一约束，先统计重复、空白和NULL，列出处理规则并由业务确认。测试副本验证回填和约束建立；不为使脚本通过而随意删除重复付款。对现存数据的“修正”可能涉及已支付事实，要保留证据。

验收应覆盖缺失金额、负数、不同币种、重复请求号、非法状态、软删除后重复与恢复冲突。约束失败不应泄露完整财务流水，也不应被统一改成“保存成功”。

## AI 易忽视的问题

- 用浮点金额加大量四舍五入补丁，没有统一精度契约。
- 把前端必填当数据库必填，批量导入绕过后产生脏数据。
- updated_at被当作完整历史；软删除被当作隐私清除或授权。
- 为了兼容导入给所有字段随意默认值。

## PM 评审问题

1. 缺失、零、空串和未知分别如何表达？
2. 金额币种、精度、舍入和输入范围是什么？
3. 默认值由谁确认，省略是否真的代表该事实？
4. 哪些状态变化需要权限、前置条件和并发检查？
5. 软删除后哪些渠道仍可读取，编号能否复用？
6. 加约束时旧脏数据如何处理并留证？

## 微实践：逐字段追问

拿一张虚构付款表，逐列写业务含义、类型、空值、默认、约束、可信来源。构造缺失金额与真实0、0012与12、删除后重建三个反例，说明哪层应拒绝或提示。
