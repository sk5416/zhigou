# Git 到底解决什么问题

## 结论先行

1. Git 为被跟踪文件记录可追溯的版本快照，帮助比较、协作和恢复代码。
2. 工作区、暂存区与提交不同；文件保存到磁盘不等于已提交，提交也不等于已推送。
3. Git 与 GitHub 等托管服务不是同一个东西，本地版本历史不依赖持续联网。
4. 代码版本控制不自动备份数据库、秘密、用户文件或所有未跟踪内容。

## 业务场景：三个“最终版”不知道该选哪个

模拟订单查询工具有“最终版”“最终版修复”“最终版新”的文件夹。AI 在一份目录修权限，在另一份加导出，维护者无法确定服务器运行哪份。文件夹复制能留下某些副本，但很难可靠说明每次改动的原因、范围和对应验证。

## 核心概念：工作区、暂存与历史

工作区是当前文件内容；暂存区记录准备纳入下一次提交的内容；提交把选定状态记录为有标识、说明及父关系的历史节点。提交不是简单的聊天摘要，也不是自动运行成功的证明。

仓库保存版本对象及相关信息。提交标识可帮助定位准确状态；分支便于组织不同工作；标签可标记重要基线。名称叫“稳定版”仍不能替代测试和发布证据。

## 工作原理：让一次改动有边界

```text
编辑文件 → 检查工作区差异 → 选择暂存 → 检查暂存差异 → 提交
                                              ↓
                              推送到选定的远端仓库
```

Git 记录的是被纳入版本控制的内容。暂存后继续编辑同一文件，提交可能仍包含较早暂存的内容，需要分别检查。未跟踪文件也不会因为点了提交就必然进入历史。

托管服务增加远端存放、访问权限、评审和自动检查等协作能力。推送将相关本地提交分享出去；它不是应用部署命令。服务器是否运行该提交，仍要通过构建产物和发布记录核验。

| 说法 | 还需要确认 |
|---|---|
| 已保存文件 | 是否被跟踪、暂存和提交 |
| 已提交 | 提交包含哪些文件，是否验证 |
| 已推送 | 推到哪个远端和分支，是否含秘密 |
| 已发布 | 哪个产物和数据结构版本实际运行 |

## 企业案例：把权限修复与页面改色分开

模拟同一批修改同时包含服务端授权修复和页面样式变化。建议按可理解的工作边界组织提交，记录授权反例测试与未验证项。若回顾时只想确认权限改动，就不必从成百行无关样式中寻找关键逻辑。

不要把一次聊天里出现的所有文件都自动提交；先保护已有未提交工作，核对每项变更的来源。数据库恢复和用户学习数据需要独立备份，不能因为源码已在 Git 就删掉数据库备份计划。

## AI 易忽视的问题

- 在错误目录修改，或未检查已有工作就覆盖文件。
- 把提交完成说成部署完成。
- 将密钥、真实测试数据和临时大文件一并纳入历史。
- 用提交数量替代改动可理解性和验证质量。

## PM 评审问题

1. 当前工作目录与仓库是否正确，已有修改有哪些？
2. 下一次提交具体包含什么，哪些内容被排除？
3. 这次改动对应哪项需求、反例和验证？
4. 远端仓库、分支与运行版本如何对应？
5. Git 不负责的数据库和用户数据由什么方式备份？

## 微实践：判断四种完成状态

模拟 AI 说“文件已保存、已提交、已推送、已上线”。为每个说法列出需要查看的独立证据。最后说明为什么从 Git 找回旧源码，仍可能无法恢复被覆盖的业务数据。
