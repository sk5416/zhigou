# 常见 Git 操作与忽略规则

## 结论先行

1. 提交前分别查看状态、未暂存差异和暂存差异，确认将记录的真实内容。
2. `pull` 获取并整合远端变化，`push` 分享本地提交；不能在未知本地状态下机械执行。
3. `.gitignore` 主要控制未跟踪文件的忽略规则，不能让已经进入历史的秘密自动消失。
4. 命令要与明确目标对应，先理解结果再执行，不能把“清理”当通用修复。

## 业务场景：以为只提交了接口，却带上本机配置

模拟 AI 使用范围过大的暂存操作，把本机数据库地址、测试导出和接口修复一起加入提交。解决办法是先审查范围与秘密，不是提交后才在 README 写“请勿使用”。

## 核心概念：读懂操作对象

以下为隔离练习仓库中的示意，路径不是对当前项目的实际操作要求。

```text
git status
git diff
git diff --cached
git add src/import_rules.py
git commit
git log --oneline
```

`status` 汇总当前状态，`diff` 通常比较工作区与暂存内容，`diff --cached` 查看暂存内容相对提交的变化。`add` 选择某时刻内容进入暂存，之后再改文件需要重新核对；`commit` 记录暂存状态，不能代替内容审查。

## 工作原理：忽略不是擦除

可以忽略构建产物、本机配置、临时缓存和个人备份，保留构建声明、课程源文件及必要版本信息。规则要按项目验证，不能用过宽模式忽略真正需要交付的文件。

若秘密已被跟踪，仅新增忽略规则不会停止历史暴露。需要先评估凭据泄露并停用或轮换，再按授权范围处理跟踪状态与历史清理。移除当前文件、改历史和消除第三方副本是不同目标，不能承诺一次提交就从互联网永久删除。

`clone` 用于获得仓库副本，`fetch` 获取远端信息而不自动把所有变化合入当前工作，`pull` 还会执行整合，具体方式取决于配置。`push` 的目标远端与分支也要确认。网络或权限失败不应默认用强制推送解决。

## 企业案例：暂存后又改了一行

模拟规则文件暂存时只验证正数量，随后又补充空值处理但未重新暂存。只看编辑器会误以为两项都将提交。建议检查 `status` 和暂存差异，确认新增规则及其测试是否真的进入本次记录。

推送前再次核对不含真实凭据或个人备份，检查远端变化是否与本地并行。如果需要整合，先保留未提交工作并看差异；不要直接丢弃本地文件让状态“干净”。

## AI 易忽视的问题

- 用广泛暂存代替审阅，忽略生成文件和本机数据。
- 看了工作区差异，却没看实际暂存内容。
- 将忽略规则当成秘密轮换与历史清理。
- 整合失败后自动覆盖文件或强推远端。

## PM 评审问题

1. 当前修改、未跟踪和暂存内容分别是什么？
2. 哪些文件应该进入版本，哪些只是本机或个人数据？
3. 提交前检查的是暂存状态还是编辑器当前内容？
4. 获取远端变化会怎样影响已有修改？
5. 推送到哪里，权限和分支目标是否正确？
6. 若秘密已提交，是否区分轮换、停止跟踪与历史处理？

## 微实践：解释一份状态摘要

模拟一个规则文件同时有已暂存和未暂存修改，另有未跟踪的备份。写出下一次提交可能包含什么、还应检查什么。练习只使用虚构配置，不创建或提交真实秘密来测试忽略效果。
