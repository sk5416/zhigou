# 索引、查询计划与慢 SQL

## 结论先行

1. 先确认慢在哪里，再考虑索引；等待锁、网络慢、返回太多数据并不都由缺索引导致。
2. 索引是为访问模式维护的额外结构，用存储和写入代价换取部分查询收益。
3. 组合索引的列顺序与过滤、范围、排序有关；不要把经验口诀当跨产品绝对定律。
4. 验证应使用有代表性的数据量和分布，检查计划、耗时及写入影响，而非只在十行样例上比较。

## 业务场景：内网查询越用越慢

模拟员工查询财务流水，最近一个月从几万行增长到百万行。AI给每个字段都建索引，又把请求超时从5秒改成60秒。查询仍慢，导入速度反而下降。首先拆分耗时：连接等待、锁等待、数据库执行、结果传输、前端渲染各用了多久？慢SQL只是链路中的一部分。

## 核心概念：扫描、选择率与计划

扫描是访问数据的方式，顺序扫描不一定错误：小表或返回大比例行时，逐行访问可能比反复索引定位更省。选择率描述条件筛掉多少数据；低区分度状态列单独建索引未必获益。

查询计划展示访问路径、连接、过滤、排序等步骤。估算行数与实际行数偏差大，可能提示统计信息或数据倾斜问题。计划中的cost通常是优化器相对代价单位，不是毫秒，不能拿不同环境数字直接当用户延迟。

## 工作原理：索引服务一类查询

模拟SQLite表ledger含org、posted_at、id、cents，访问模式为指定组织按日期倒序取最近50行。时间使用固定宽度、统一UTC格式文本，避免混合格式造成顺序错误。

```sql
CREATE INDEX ix_ledger_recent ON ledger(org, posted_at DESC, id DESC);
EXPLAIN QUERY PLAN
SELECT id, posted_at, cents
FROM ledger
WHERE org = 'O1'
ORDER BY posted_at DESC, id DESC
LIMIT 50;
```

前导org等值过滤后，日期与id提供稳定排序。若主要查询改成不分组织的全局最近记录，此索引不保证同等收益；需看实际计划。PostgreSQL18的B-tree还有skip scan等优化，不能绝对断言“未用第一列就永不走索引”。函数、隐式类型转换、模糊匹配和范围条件也可能改变可用路径，具体看产品版本与计划。

| 观察 | 可能方向 | 下一步证据 |
|---|---|---|
| 结果仅50行却处理海量行 | 过滤/排序路径不匹配 | 看访问路径及处理行数 |
| 大量时间在等待 | 锁、连接池或资源争用 | 看等待类型和阻塞链 |
| SQL快但页面慢 | 传输或渲染 | 比较分段耗时与返回字节 |
| 估算与实际差距大 | 分布、统计或参数敏感 | 代表性参数与计划对照 |

深OFFSET分页仍可能处理大量被跳过的行，可在业务允许时考虑游标式分页，使用稳定唯一排序键，并定义并发新增或删除时的页面语义；不能仅换语法就宣称永不漏行。

普通EXPLAIN多展示估算；PostgreSQL的EXPLAIN ANALYZE会真正执行语句，包括写语句的副作用与锁。不要为看计划直接在生产运行写入或重型查询，即使用事务回滚也不能撤销所有外部影响。本文SQLite示例用EXPLAIN QUERY PLAN，不声称输出真实耗时。

## 企业案例：证明收益再保留索引

模拟在脱敏测试副本构造常用组织与大组织、近月和历史查询，记录优化前后计划、耗时分布、返回量及批量导入成本。用相同条件比较，区分冷缓存与热缓存；如未解决瓶颈，应撤销无收益索引，继续查阻塞或查询范围。

索引不是授权。org条件不能由客户端任意指定；性能优化时也不能删服务端组织范围校验。缩短SQL不应扩大员工可见数据。

## AI 易忽视的问题

- 全字段加索引、凭列名推荐，忽略实际WHERE与ORDER BY。
- 只报平均耗时，掩盖慢尾部、数据倾斜和写入退化。
- 把扫描视为一定失败，把cost解释为毫秒。
- 测试十行数据后宣称百万行性能已验证。

## PM 评审问题

1. 延迟来自执行、等待、传输还是渲染，有何证据？
2. 最常用与最极端查询参数分别是什么？
3. 索引列顺序与过滤、范围和排序怎样对应？
4. 数据量、分布、冷热缓存与生产差异多大？
5. 写入、存储与维护成本是否被测量？
6. 查看实际计划会否执行副作用或造成阻塞？

## 微实践：阅读计划而不猜快慢

用隔离SQLite虚构ledger数据，比较建索引前后上述查询计划。记录有没有临时排序、访问路径怎样变化；小数据结果只证明语法和可观察路径，不外推生产延迟。不要连接真实财务库。
