# 异常处理、日志与调试

## 结论先行

1. 捕获异常是决定如何处理或传递错误，不是让失败变成成功。
2. 输入问题、程序缺陷、依赖故障和结果未知需要不同处置，不能统一“再试一次”。
3. 日志应连接时间、业务标识与请求链路，同时避免秘密和无关敏感数据。
4. 有效报障包含版本、步骤、预期、实际和脱敏证据，比“不能用”更能帮助定位。

## 业务场景：接口返回成功，文件却没有导入

模拟青禾制造的文件导入遇到解析错误。AI 为了页面不报红，捕获全部异常并返回成功。用户以为入库，后续对账才发现缺失。程序没有崩溃，不代表业务动作成功；需要先定义失败如何对用户、日志和任务状态表达。

## 核心概念：异常、传播与证据

语法错误使程序不能按预期解析；运行时异常则在执行中出现。堆栈说明经过的调用位置及错误类型，是定位线索，不是所有行都需要修改。最后一行通常给出异常类型与信息，仍需结合完整上下文判断根因。

错误可以在合适边界被处理：输入转换失败可返回字段错误；临时依赖故障可在明确条件下重试；未知错误可记录必要上下文并向上层传播。若无法恢复，就不应返回虚构成功。清理文件句柄等资源的动作也应在异常情况下完成。

## 工作原理：分开用户反馈与内部诊断

下面是错误做法的模拟片段，函数由业务环境提供，并非可直接运行的完整程序。

```python
def run_import():
    try:
        import_file()
    except Exception:
        # 错误示例：失败被伪装成成功
        return {"success": True}
```

更合理的是对可预期输入错误给出行号、字段和原因；对未知故障记录关联标识和异常，再返回稳定错误结果或继续抛出。不要把含口令的连接串、完整银行流水、访问令牌或内部堆栈直接发给普通用户。

日志级别帮助表达诊断用途和严重程度，不是“越高越完整”。调试细节适合受控排查；正常状态记录可用于追踪；警告与错误需要能解释影响。大量重复错误会淹没线索，应结合请求编号、采样或汇总控制噪声，但不能通过删除失败证据美化结果。

模拟日志可以写为：`request=R17 batch=B03 stage=parse row=12 result=rejected reason=invalid_quantity`。这些标识是虚构的，既能关联事件，也不必保存全部原始内容。

## 企业案例：从现象缩小到根因

模拟报障说明：“dev.3；导入虚构文件，12行数量为文本；预期逐行拒绝，实际整批提示成功；关联 R17；解析阶段出现类型错误”。这比粘贴一屏完整生产数据更有效。

沿堆栈确认入口、解析与业务层，复现后补测正常记录、无效行、空文件、依赖中断和结果未知。修复后检查页面反馈、任务状态及日志一致。写入发生后才异常时，还要核实哪些数据已提交，不能仅按异常存在就把所有行算未执行。

## AI 易忽视的问题

- 捕获最宽泛异常后返回空列表或成功，掩盖故障。
- 在多个层级反复记录同一异常，造成噪声。
- 将原始请求和凭据整体打印，误认为日志越多越安全。
- 只验证不再报错，未验证业务状态和数据结果。

## PM 评审问题

1. 当前错误属于哪类，依据是什么，哪些结果仍不确定？
2. 哪一层负责处理、传播和用户反馈？
3. 日志能否关联业务动作，是否保留了不必要的秘密？
4. 哪些数据可能已经写入，如何核实？
5. 修复如何复现和验证，是否覆盖失败路径？
6. 可交接的报障材料是否包含版本和最小步骤？

## 微实践：写一份有效报障

用虚构批次描述“第12行解析失败但页面提示成功”。列出版本、操作、预期、实际、时间、关联编号和脱敏错误；再写需要 AI 回答的两项未知。不要要求 AI 从模糊截图猜测整个运行环境。
