# IP、域名、DNS、端口与内网边界

## 结论先行

1. 地址解析、网络可达、端口监听、TLS 校验和应用授权是不同层次，不能互相代替证明。
2. `localhost` 指发起访问的设备自己；员工手机上的本机地址不指向开发者电脑。
3. 内网、公网与 VPN 描述访问条件，不自动赋予访问者业务权限。
4. 排错应逐段收集证据，不能默认关闭防火墙、开放所有端口来“修复”。

## 业务场景：服务器自己能开，员工却不能

模拟青禾制造在服务器浏览器中打开订单网站成功，员工电脑访问失败。可能是员工使用了自己的 `localhost`，也可能是名称解析、路由、入口规则或监听地址不同。先画出员工到服务器的访问路径，再确定失败在哪段，比让 AI 同时修改五项配置更可控。

## 核心概念与系统位置

**IP 地址**用于网络寻址，**域名**为访问目标提供可管理的名称，**DNS**负责名称到相应记录的解析。一个域名可以关联多个地址，地址也可能随环境变化；解析结果不是永久写死的事实。

**端口**帮助区分设备上网络服务的入口；进程必须在相应协议、地址与端口监听。绑定回环地址通常仅供本机访问，绑定其他接口会改变可访问范围，但仍受路由和防火墙等限制。不能仅凭端口号断言使用了正确的 TLS 或业务协议。

**防火墙**控制网络访问规则，**VPN**可在适当配置下提供到特定网络的连接路径。它们不能替代应用的身份认证、部门数据授权和凭据保护。

## 工作原理：按访问链路找证据

```text
员工设备 → 名称解析 → 路由/VPN/防火墙 → 指定地址与端口
        → HTTPS 入口与证书 → 应用身份/授权 → 数据源
```

| 现象 | 可以先核查什么 | 不能直接推断什么 |
|---|---|---|
| 名称找不到 | 实际域名、DNS 配置及解析结果 | 应用代码有错 |
| 连接被拒绝 | 地址、端口、监听进程和入口规则 | 数据库口令一定错 |
| 等待超时 | 路由、规则、依赖及超时发生位置 | 对方一定没有处理请求 |
| 证书错误 | 名称、信任和有效期 | 关闭校验后就算安全 |
| 返回无权访问 | 身份、授权与响应来源 | 网络一定不通 |

`ping` 成功通常只能提供特定网络探测的证据，不证明目标 Web 端口可用；探测失败也可能是 ICMP 被限制，不能单凭它判定 HTTP 不通。若使用 IP 替代域名测试 HTTPS，还可能改变证书名称匹配和代理路由条件，不能混为完全相同的验证。

## 企业案例：收窄修复，不扩大暴露

模拟发现服务仅监听本机回环地址。错误修复是监听所有接口并关闭防火墙，随后把访问成功当完成。建议明确批准的入口、允许来源和服务角色：若应用只应由同机反向代理访问，保留本机监听可能正是正确设计；员工访问代理入口即可。若确需跨机连接，再按实际来源和端口配置最小访问范围。

验证分别从批准和未批准来源访问，检查目标进程、入口日志、TLS 及普通员工数据范围。模拟域名 `query.example.test` 仅为说明，不代表真实地址或保证能在你的网络解析。

## AI 易忽视的问题

- 将开发地址复制到用户设备，忽略请求发起位置。
- 把可达性故障用无限权限和永久关闭防护处理。
- 混淆代理入口、应用内部端口和数据库端口。
- 将内网或 VPN 用户都视为同一可信业务角色。

## PM 评审问题

1. 谁从哪台设备，经什么路径访问哪个入口？
2. 实际域名解析到哪里，服务监听哪个地址与端口？
3. 哪些来源应允许，哪些来源应拒绝？
4. 代理和应用原始端口是否有不同访问边界？
5. 当前证据证明到哪一层，尚未证明什么？

## 微实践：拆解三份报障

模拟甲用手机访问 `localhost`，乙使用正确域名但证书不受信任，丙登录成功却能查其他部门订单。分别指出首先核查的是设备与地址、TLS 信任、服务端授权。不要用同一条“检查网络”覆盖三种问题，也不要要求真实企业地址才能讨论。
