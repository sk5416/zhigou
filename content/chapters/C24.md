# 事务、锁、并发与数据一致性

## 结论先行

1. 把相关写入放进事务能减少部分成功，但业务规则仍要由约束、条件更新和正确的并发策略保证。
2. 两个人同时“先读再写”会互相覆盖；单人演示不能验证并发正确性。
3. 锁、版本校验和隔离级别各有适用范围，不能只加一句BEGIN就宣称解决并发。
4. 本地事务不会把远程ERP调用纳入同一个原子提交；超时结果未知仍须查询、幂等与对账。

## 业务场景：两人审批把库存扣成负数

模拟库存仅余5，甲乙各申请4。两边先查“库存>=4”为真，再分别扣减；若没有写入时条件和正确并发控制，可能超卖或覆盖彼此结果。测试不能只按顺序点两次，要构造两个执行者读取同一旧状态的交错。

## 核心概念：ACID与业务不变量

原子性指事务范围内操作一起提交或回滚；一致性依赖约束和业务代码维护规则；隔离性处理并发执行的可见性；持久性依赖数据库和存储配置保障已提交结果。ACID不替你定义“库存不能负数”或“不能越权审批”。

提交使事务结果生效；回滚撤销其范围内未提交的数据库变更，不等于撤销已发邮件、远程付款或所有外部副作用。某些数据库的DDL提交行为也不同，需按产品核实。

## 工作原理：把前提放进写入

模拟SQLite库存表stock含sku、qty、version。连接不在其他事务内，qty为整数且限制非负。参数均来自已校验输入，下面SQL只演示一次条件更新。

```sql
BEGIN;
UPDATE stock
SET qty = qty - 4, version = version + 1
WHERE sku = 'M1' AND qty >= 4 AND version = 1;
```

应用必须立即检查该UPDATE的影响行数：1才表示本次更新成立；0代表不存在、数量不足或旧版本冲突，需区分反馈并回滚，不能继续创建“已扣减”单据。后续本地单据写入成功后才能COMMIT，失败则ROLLBACK。本段故意不自动提交，微实践分别验证提交和回滚分支。

版本校验是乐观并发控制：提交时要求仍为读取版本，冲突后重新读取并请用户确认或按明确规则重算；不是自动用旧值再覆盖。悲观锁则在数据库支持的范围内提前锁定要修改的数据，可能等待或死锁，应缩短事务、统一顺序并处理超时。SQLite不是行锁数据库，不要将其他产品的SELECT FOR UPDATE直接照搬。

| 风险 | 含义 | 需要关注 |
|---|---|---|
| 脏读 | 读到他人未提交值 | 隔离级别与实现 |
| 不可重复读 | 同事务重读的行发生变化 | 快照及隔离语义 |
| 幻读 | 同条件结果集合变化 | 谓词与隔离实现 |
| 更新丢失 | 基于旧值覆盖他人结果 | 条件更新、版本或锁 |

同名隔离级别在不同数据库实现存在差异。PostgreSQL18的Read Committed每条语句可有新快照，Repeatable Read仍可能有序列化异常；Serializable可能拒绝冲突事务，需要安全地重试整个事务。隔离级别不是“越高越无需设计”，也有性能与冲突成本。

## 企业案例：本地成功与远程未知分开

模拟先扣本地库存再调用ERP建单，ERP超时。本地ROLLBACK不能保证ERP没建单；不能继续盲目重发。应为业务请求设置稳定身份，持久记录待发送/处理中/待核对等状态，使用外部可用的查询和幂等能力，无法确认时进入人工对账。这里不是宣称某ERP具有某个接口。

验收至少含：两个旧版本同时修改、影响行数0、第二笔本地写入失败、死锁或忙等待、提交后响应丢失。重试只针对可重试错误并设置上限，事务内避免长时间等待外部网络。

## AI 易忽视的问题

- 先查再写却不校验版本或影响行数；冲突仍提示成功。
- 捕获异常只记录日志，随后照常提交其他步骤。
- 把数据库事务当跨服务事务，忽略远程未知结果。
- 用sleep模拟并发，未保证两个执行者真的读到同一旧状态。

## PM 评审问题

1. 本业务必须始终成立的不变量是什么？
2. 事务包含哪些写入，哪些副作用在范围外？
3. 两个旧版本交错提交时，谁被拒绝、用户看到什么？
4. 影响行数0与异常分别怎样处理？
5. 锁超时、死锁和重试是否有限且可观测？
6. 远程调用已执行但本地未确认时如何核对？

## 微实践：让第二次旧版本更新失败

在临时SQLite中建M1库存5、version1。第一次执行条件更新后提交，验证库存1、version2；第二次仍以version1执行，影响行数应0。再把库存重置为隔离练习初值，在扣减后主动回滚，验证库存与版本均恢复。此顺序实验验证旧版本冲突和原子性，不等于已跑完真实双连接并发压力测试。
