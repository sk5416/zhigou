# 架构决策记录与技术债

## 结论先行

1. 重要选型要记录当时前提、备选、证据、代价与重评条件，后续才能判断何时改变。
2. 技术债是延后某项改进所承担的持续成本或风险；可以有意识接受，但应有责任人和触发条件。
3. 重构改善内部结构且意图保持外部行为；重写引入更大的迁移和验证范围，不能仅凭代码不好看决定。
4. 决策记录保留被替代的历史，不把事后知道的结果冒充当初已验证的事实。

## 业务场景：半年后没人知道为什么不用队列

模拟原工具每天只执行一次、耗时数秒，因此选择持久任务表和简单后台处理。半年后要处理大量任务，AI看到“没有消息队列”就指责原设计错误。若当时前提、可接受延迟和重评阈值有记录，就能解释：原方案可能在当时合理，当前变化需要新证据，而不是重写全部系统。

## 核心概念：决策、债务与普通待办

ADR即架构决策记录，通常一份记录一项重要取舍。它不是完整设计书，也不是会议纪要堆积。可用简短编号文档表达；格式服务于理解，不要求引入新系统。

技术债不同于所有未完成功能。比如暂缓自动恢复演练会增加故障风险，需要明确承担者和补足时间；新需求“增加统计图”本身未必是债。已知高危缺陷也不能仅贴“技术债”标签长期搁置，应按风险处理。

## 工作原理：把条件与证据写在决定旁边

以下为虚构决策示例，不是对本App额外增加在线功能的指令。

| 字段 | 示例内容 |
|---|---|
| 编号与状态 | ADR-007，已接受，日期与负责人 |
| 问题与硬条件 | 每日一次本地批处理，需重启后可继续，单人维护 |
| 候选 | 进程内内存任务、持久任务表、独立消息代理 |
| 证据 | 隔离样例验证任务表重启恢复；未做高并发压测 |
| 决定与代价 | 选持久任务表，避免当前多组件运维；接受手动处理少量失败 |
| 风险与重评 | 积压持续超出业务时限、需要多个消费者时重新评估 |

证据应链接具体版本、检查和限制，不写“已充分验证”而无范围。接受某个缺口需记录风险、责任人、处理计划或触发条件；并非所有事情都要立刻做，但必须知道省略了什么。

重评时追加新决定说明原前提怎样变化，旧ADR标为被替代并链接新记录，而不是改写过去的理由。原方案的已知限制与本次发现的问题也应区分，避免让后来的维护者误认为风险早已被验收。

## 企业案例：以边界清楚的重构替代无依据重写

模拟AI建议为修复重复导入而重写前后端并换数据库。先定位重复来自请求身份、防重约束还是事务边界，再比较局部修复、模块重构和整体迁移。若局部方案能满足验收，不应把大改当成默认最优；若现结构确实无法维护，也需提出渐进迁移、旧行为对照、数据兼容与回退证据。

建立需要保持的行为基线：权限范围、金额规则、重复提交、历史与恢复。每步检查差异和影响，保留可工作的版本；测试覆盖不足时先补高风险可观察证据，不能一边重写一边假定所有旧行为都不重要。

## AI 易忽视的问题

- 只有技术名称，没有前提、备选与代价。
- 把未实测的性能和兼容能力写成已验证。
- 债务没有责任、期限或触发条件，永远不偿还。
- 重写时删除历史与迁移，用新功能正常截图替代旧行为回归。

## PM 评审问题

1. 这项决定解决什么问题，硬条件是什么？
2. 至少比较过哪些现实可选方案？
3. 哪些依据已验证，哪些仍是假设？
4. 接受了什么代价或债，谁负责何时重评？
5. 重构或重写是否有局部替代方案？
6. 旧数据、权限与行为如何对照和回退？

## 微实践：留下“为什么”的版本

为虚构财务导入工具写一页ADR，选择是否引入缓存或队列。至少保留一个被否决备选、一项未验证假设和一个重评触发；随后模拟负载变化，追加新决定而不是覆盖原记录。
