# 代码如何运行，以及为什么换电脑就坏

## 结论先行

1. 代码文件、构建产物与运行中的进程是不同对象；“文件都复制了”不能证明服务能运行。
2. 运行依赖、配置、权限、目录和网络条件都可能与开发机器不同。
3. 可重建的环境说明比复制整个开发目录更可靠，但仍需在目标环境实际验证。

## 业务场景：换台电脑后导出失败

模拟订单工具在开发者电脑正常，交给维护者后报“找不到模块”，修复后又因写入桌面目录失败。业务 SQL 没变，但程序依赖的库、启动目录、输出权限和配置路径不同。应先确认差异，避免让 AI 为消除报错盲目重写查询逻辑。

## 核心概念与系统位置

**源代码**描述逻辑；**运行时**为程序提供执行环境；**依赖**是它调用的外部库或组件。某些程序先经过构建、编译或打包生成**产物**，目标机器应运行匹配的产物与必要环境，不是随意双击任意源码。

**进程**是已启动的执行实例。Web 服务还可能监听指定地址和端口。存在源码、安装了运行时、进程已启动、端口可达、业务可用，是逐步增强且需要分别验证的事实。

**配置**提供环境差异，如模拟数据库地址、输出目录和超时。环境变量是配置传入方式之一，不是自动保密机制；谁能读取进程、日志或诊断信息仍需管理。

## 工作原理：将环境拆成六类核对

| 核对项 | 模拟差异 | 应保留的证据 |
|---|---|---|
| 运行时/系统 | 版本或平台不匹配 | 实际运行版本与支持范围 |
| 依赖 | 本机有库，目标机未安装 | 依赖声明、锁定版本、安装结果 |
| 启动方式 | 工作目录不同 | 明确入口、参数与启动目录 |
| 配置 | 指向开发数据库 | 配置来源和脱敏的环境标识 |
| 文件权限 | 服务账号不能写目录 | 账号及目标目录权限检查 |
| 网络 | 只监听本机回环地址 | 监听地址、端口和访问路径 |

例如 Python 虚拟环境隔离某个项目的包依赖，通常应依据声明在目标位置重建，不把开发者的整个虚拟环境目录当可移动交付包。这个例子用于理解依赖，不规定知构必须使用 Python。

依赖锁定有助于重现版本，不保证库永远可获取、所有平台一致或配置正确。容器也需要持久化、权限和配置设计；把环境问题换一种包装不会让责任自动消失。

## 企业案例：先排环境，再动业务逻辑

模拟维护者启动工具时报错缺少库。建议先记录完整但不含秘密的错误类型、运行版本、启动命令和工作目录，在隔离目录按声明安装依赖；再运行最小验证。随后用虚构数据确认输出位置可写、错误能反馈。

若进程启动却手机无法访问，先看服务是否只绑定 `127.0.0.1`、手机与服务器网络是否可达，再评估访问控制。不能直接“监听所有地址并关闭防火墙”作为通用修复。扩大可达范围会改变信任边界，需要明确允许来源。

## AI 易忽视的问题

- 使用开发者专属绝对路径或全局安装的库，未写入交付说明。
- 将 `.env` 或完整环境变量输出贴进日志，泄露秘密。
- 忽略服务账号与交互登录账号的权限差异。
- 为解决版本冲突直接升级全部依赖，破坏已知可用组合。

## PM 评审问题

1. 交付的是哪些产物，目标环境还需要安装什么？
2. 入口、启动目录、参数和服务账号是否明确？
3. 依赖如何固定和重建，是否在干净环境试过？
4. 配置从哪里来，如何确认不会误连生产？
5. 失败时应看哪些日志，如何避免暴露凭据？
6. 进程、端口可达和业务可用分别如何验证？

## 微实践：读一份模拟交接单

交接单只有“运行 main.py”，启动后提示缺少模块；开发者说“把我的整个文件夹复制过去”。请补出运行版本、依赖声明、入口目录、配置样例、数据与输出路径、账号权限和最小验证步骤。每项说明为什么缺少它会导致差异，不需要真的安装软件或连接企业系统。
