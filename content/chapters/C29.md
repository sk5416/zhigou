# 表单、批量导入与校验

## 结论先行

1. 前端校验帮助及时纠错，服务端校验决定是否接受；任何客户端都不能替服务端作可信保证。
2. 批量导入必须有稳定的行号与结果规则，明确整批原子还是逐行部分成功。
3. 文件名、扩展名和浏览器报告的类型都不能独立证明文件可信；大小、格式、内容和处理资源要共同限制。
4. 重复点击、响应丢失和重试要靠明确的业务身份防重，禁用按钮只能减少误操作。

## 业务场景：一千行中三行失败

模拟财务导入1000行流水，界面只显示“导入失败”。实际997行已入库，用户改完三行重传全部文件，生成重复流水。需要先定义提交单位和逐行结果，而不是先写一个catch把所有错误变成同一句话。

## 核心概念：校验层与结果契约

格式校验检查是否可解析，字段校验检查必填、类型和范围，业务校验检查组织、状态、关联与权限，数据库约束保护能表达的不变量。前端可重复一部分规则以改善体验，服务端仍须对每次请求执行必要检查；否则绕过页面即可提交非法值。

校验不是自动“修好”数据。把空金额改零、截断编码、把日期猜成另一种区域格式都可能改变事实。允许的归一化要公开说明，并保留可核对的原始定位；不能静默修改再计成功。

## 工作原理：先约定一行的身份和命运

模拟CSV导入结果，第一行为表头，数据原始行号从2开始；导入ID代表一次业务意图，row_key代表该意图中稳定的一行。以下JSON仅是模拟结果，不是任何ERP厂商接口。

```json
{
  "import_id": "IMP-DEMO-01",
  "policy": "partial",
  "rows": [
    {"line": 2, "row_key": "R1", "status": "accepted", "record_id": "B101"},
    {"line": 3, "row_key": "R2", "status": "rejected", "field": "amount", "code": "REQUIRED"}
  ]
}
```

accepted必须对应已持久确认的结果，不能只是“已排队”。异步处理时应另有pending/processing等状态、查询方式与最终结果；超时后状态unknown不能擅自改成rejected。行结果应满足可核对的数量关系，并记录重复跳过等额外状态的明确定义。

整批原子适合必须一起成立的集合，任一不合法即整体拒绝；部分成功适合可独立处理且业务接受补正的行，但每行也要有自己的事务、防重及审计。预览通过后到正式提交之间数据可能变化，提交时仍需必要复核，不能相信预览是永久许可证。

文件接收先限制请求与解压后大小、行数、列数、类型及处理时间，服务端验证实际内容。扩展名白名单和MIME检查是分层手段，单独都不充分；隔离暂存、受控命名、不可执行存储与权限也需设计。压缩炸弹、巨大单元格、恶意公式或危险解析特性都可能耗尽资源或引入后续风险；选项按业务必要性开放，不默认支持所有办公格式。

错误报告导出CSV时，用户文本可能以公式前缀开头，电子表格软件可能解释为公式；应按目标工具设计安全输出，不能仅因源文件是CSV就认为无执行风险。教材不提供万能清洗规则。

## 企业案例：仅重试失败的业务行

模拟先把1000行分别标记已确认成功、明确拒绝和结果未知。用户修正被拒绝的行，服务端按明确定义的新尝试或业务身份提交；已成功行不重复入账，未知行先查询或对账。仅按文件名或上传时间防重不足，同一业务可能换文件名再次提交。

验收包括空值、前导零、重复业务键、同文件重复、行号偏移、表头变化、超大输入、预览后权限变化、提交成功但响应丢失。用虚构数据验证每种结果，不把“页面报错”当作“没有写入”。

## AI 易忽视的问题

- 只有HTML必填或前端校验，直接调用接口可绕过。
- 1000行共用一个“失败”状态，不知道已写多少。
- 处理器跳过空行后重编行号，用户无法定位原文件。
- 按文件名去重，或把未知结果全部重传。
- 把未经验证的文件直接存为可执行路径或公开链接。

## PM 评审问题

1. 哪层保证哪些规则，绕过页面如何拒绝？
2. 整批还是逐行提交，结果数如何核对？
3. 原始行号、业务键和重试身份怎样保持？
4. 预览后数据或权限变化如何处理？
5. 上传和解析资源限制、暂存保留与访问策略是什么？
6. 结果未知、成功重复和明确失败分别怎样恢复？

## 微实践：做一份五行反例文件

用虚构CSV构造正常、空金额、重复业务键、前导零编码和错误日期五行，先写出整批与部分策略下各自期望结果。核对原始行号及数量，再模拟响应丢失，说明不能凭错误弹窗断定未入库。
