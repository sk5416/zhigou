# 关系型数据库与数据关系

## 结论先行

1. 表的关联首先是业务身份与责任边界问题，再由主键、唯一约束和外键表达。
2. 内部主键不等于业务编号；跨组织、跨系统的编号必须说清唯一范围。
3. 页面上先查再新增不能抵御并发重复，数据库约束是最后一道一致性防线。
4. 文档型、键值型等非关系存储并不天然更快或更灵活；选择取决于访问模式、约束和维护成本。

## 业务场景：两套系统都叫项目1001

模拟数仓整合甲ERP与乙CRM，两边都有编号1001的项目。AI用编号直接连接，报表行数看似正确，却把乙公司的费用归到甲公司。问题不是JOIN语法，而是没有确定对象身份：编号在哪个来源、组织和期间内唯一？同名项目是否真是同一对象？

## 核心概念：身份、关系与约束

主键唯一标识表中的一行，通常要求非空。内部代理键如整数ID便于引用；业务键如“组织+物料编码”表达业务唯一性。采用代理键后仍需保留业务唯一约束，不能因为每行ID不同就允许同组织物料重复。

外键表达引用的父对象存在，不代表“引用者有权限”“订单状态允许开票”。一对多如订单与明细，多对多如用户与角色应通过关联表表达，关联表可再限制同一用户角色组合不重复。

| 约束 | 能保证什么 | 不能替代什么 |
|---|---|---|
| PRIMARY KEY | 行身份唯一且非空 | 业务编码正确、业务上不重复 |
| UNIQUE | 指定列组合的唯一规则 | 缺失值策略、跨系统匹配判断 |
| FOREIGN KEY | 引用满足数据库定义的关系 | 行级授权、外部API对象存在 |
| CHECK / NOT NULL | 本行条件、必填边界 | 跨服务流程和复杂跨行规则 |

## 工作原理：让错误写入失败

以下为SQLite隔离练习语法；真实数据库需按方言确认类型、排序规则、空值唯一性和约束开关。SQLite连接应在事务开始前启用并核对外键，不能只看DDL写了REFERENCES。

```sql
PRAGMA foreign_keys = ON;
CREATE TABLE project (
  id INTEGER PRIMARY KEY,
  source TEXT NOT NULL,
  org TEXT NOT NULL,
  code TEXT NOT NULL,
  UNIQUE(source, org, code)
);
CREATE TABLE expense (
  id INTEGER PRIMARY KEY,
  project_id INTEGER NOT NULL REFERENCES project(id),
  cents INTEGER NOT NULL CHECK(cents >= 0)
);
```

project表允许不同来源或组织使用相同code，却拒绝同一范围重复。expense不能引用不存在的project；删除父对象的行为要明确选择拒绝、级联或置空，本例默认拒绝仍被引用的父行。不要为了“删除方便”给所有关系配置级联删除。

跨ERP与CRM的引用通常无法由本地外键直接强制，需要本地映射表记录来源身份、内部ID、匹配依据和待确认状态。模糊名称不能静默合并。唯一约束受字符大小写、尾空格、NULL等产品规则影响，须用边界数据验证。

非关系型并非没有结构：文档存储适合按完整聚合读取且字段变化多的对象，但跨文档关联、一致性与索引仍要设计；键值存储适合已知键访问。关系型也能支持JSON。不要以“以后会灵活”为由放弃当前清晰的业务约束。

## 企业案例：用映射替代名称猜测

模拟将源身份(source, org, code)映射到统一项目ID，人工确认业务上确为同一项目后才合并。冲突先进入待确认清单；报表保留来源，未知映射不默认归入第一个同名项目。

验证包括同码异源、同源同组织重复、孤儿费用、父项删除、重复导入及并发新增。拒绝写入应返回可理解的冲突信息，记录必要定位号，而非删约束让导入“全绿”。

## AI 易忽视的问题

- 只有自增ID，没有业务唯一约束；名称相等即认作相同对象。
- 外键未启用，或者把外键误当数据权限。
- 多对多列表塞进逗号分隔字符串，难以去重与维护关联。
- 跨系统对象暂未同步就永久丢弃明细，缺少待确认与重处理路径。

## PM 评审问题

1. 每个业务编号在哪个来源和组织范围唯一？
2. 内部ID与业务编号改变时，关联分别如何保持？
3. 哪些约束由数据库保证，哪些需服务或对账保证？
4. 父对象删除、停用和更名各会影响什么？
5. 先查再写的并发窗口由什么阻止重复？
6. 孤儿数据、映射冲突和授权失败是否分别处理？

## 微实践：画出来源与映射

用虚构甲ERP项目1001与乙CRM项目1001，分别列出源身份、内部项目ID、映射状态和一条费用。尝试写入同范围重复键与不存在的父ID，观察应拒绝的位置；不要连接真实企业库。
