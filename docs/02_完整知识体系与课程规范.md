# 完整知识体系与课程内容规范
> 文件性质：课程范围、课程目录与内容质量标准。仅讨论**学什么、学多深、怎么解释、怎么考核**；Android App 的工程实现由 Codex 独立判断。  
> 版本：V1.0｜日期：2026-10-31

## 一、课程定位与规模

课程名称：**《AI 时代技术型 IT 项目经理：Vibe Coding 所需的软件工程全景》**  
课程主旨：**懂业务，能驱动 AI 交付；懂技术边界，能独立评审风险。**

- **15 篇课程**（第 0～14 篇），**C00 导学 + C01～C72 共 72 章正课**，另有 **8 个附录**。
- 沿用以往制定的技术基础教材主线；针对“AI 生成的功能没问题，但安全、运维、可靠性等工程问题遗漏”的现实目标，强化 **安全、非功能需求、AI 审查、故障与验收**。
- 每章描述学习主题和掌握标准。目录仅是**课程内容范围**，其中出现的 Python、Docker、HTTP、数据库等均是**应学习的技术概念/实践内容**，**不意味着学习 App 应使用这些技术实现**。
- 目录重视“关联”而不是词条堆砌。教学中不应把每章缩减为几段泛泛概念解释，也不应强求每位学习者从头独立实现复杂软件。

## 二、为什么分层、如何标记

本目录统一使用 `L1 / L2 / L3` 表示学习深度，`P0 / P1 / P2` 表示学习重要度；定义以 `01_学习者背景与学习目标.md` 为准。

- L3 最重要：能审查技术方案、识别危险遗漏、写出完整要求、使用 AI 辅助完成常规任务并核验。
- L2：能看懂并在帮助下操作，不追求完全脱离 AI。
- L1：建立概念与适用边界，不以专家式实现为目标。
- P0 是与当前 Vibe Coding 风险最直接相关的内容；P1 保证系统性；P2 扩展视野。
- 对已熟悉的 ERP、流程和常见 SQL 基础可用诊断题跳过重复讲解，但**数据库迁移、并发、恢复、最小权限等工程知识不能因“懂 SQL”而自动跳过**。

## 五、每章的内容要求

章节不需要机械追求相同篇幅，但**不能缺少**以下教学要素：

1. **结论先行**：3～5 条能真正用于技术判断的结论。
2. **业务场景**：为什么学习者会在 ERP/CRM/数仓/内部工具中遇到这个问题。
3. **核心概念与系统位置**：是什么、放在哪、与相似概念的区别。
4. **工作原理和关键边界**：何时用、何时不用、引入成本以及常见失败方式。
5. **一段企业案例**：错误做法、风险、建议思路、为何这样判断、如何验证。
6. **AI 易忽视的问题**：重点指出仅追求功能时最容易遗漏的工程要求。
7. **PM 评审问题**：5～10 个可以用于审查 AI 输出或与技术人员沟通的具体问题。
8. **可选微实践/观察任务**：如阅读一次 HTTP 请求、检查代码改动、从模拟日志定位错误、判断一个接口设计；每章按需设置，不强迫所有章节写完整项目。
9. **选择题与解析**：按第六节规范。
10. **本章小结及知识联系**：本章与前置章节、后续章节怎样关联。

### 讲解的好坏如何判断

- **合格**：学习者学完后，能识别一个业务场景中的技术风险，知道应向 AI 追问什么。
- **不合格（过浅）**：只是解释“JWT 是一种令牌”“Docker 是一种容器”，没有讲工程边界、风险和判断。
- **不合格（过深）**：陷入加密数学、操作系统内核、编译原理、复杂分布式一致性证明等与当前目标无关的专业细节。
- **不合格（误导）**：把“JWT 一定优于 Session”“内网系统无需 HTTPS”“所有密码请求体必须自己先加密”“前端不显示按钮就是权限管控”等说成定论。
- **不合格（不可信）**：没有证据就编造金蝶、Salesforce、宜搭产品行为或真实运行结果。

内容默认用自然中文表达，英文术语首次出现写中文解释；可适当使用图、对照表、示例代码，但每个示例都应支持理解和评审能力。

## 六、选择题题库与解析规范

### 1. 题型与数量

- 题型为**单选题与多选题**，无须把判断题、简答题作为主交互方式；判断类知识可改写为单选/多选。
- 每章**建议 8～12 题**，基础类章节可以略少，安全、API、AI 审查、集成可靠性等章节可略多。
- 比例以**概念辨析 25%、方案判断 35%、企业场景应用 40%**为参考；不要机械凑数。
- 每题应绑定章节与知识点；题目难度应与学习深度匹配，并能区分“知道名词”和“能作正确判断”。

### 2. 题目必须具备的内容字段（语义要求，不规定 App 存储格式）

- 稳定题目编号、关联章节、关联知识点；
- 单选/多选标记、完整题干与必要背景；
- 选项及明确答案；
- **正确选项为什么对、每个错误选项为什么错**；
- 常见误区/关键判断依据；
- 难度与考察能力（概念、判断、场景）。

Codex 可自行决定这些教学数据如何存储或在 App 中呈现。

### 3. 出题质量红线

- 选项必须互斥或有清晰边界，多选题需要声明“可选多个答案”。
- 不能靠字数、语气或“以上都对”等形式猜答案。
- 不出现模糊的“通常最好”但不给前提的技术选型题。
- **不可将复杂安全问题简化为一个教条**；HTTPS、Hash、SSO、JWT、CORS、CSRF 等必须准确。
- 设计“看上去功能正确，实际存在安全/可靠性隐患”的错误方案作为有效干扰项。
- 同章题目应覆盖不同知识点，不能只是同一道题换措辞。
- 答案与解析应能在离线状态下阅读，不依赖联网检索或在线 AI 判分。
- 若存在随时间变化的版本行为、最佳实践或平台细节，应清晰标注适用条件，避免过时误导。

### 4. 示例：不是“背答案”，而是学会判断

**C12 + C43 + C47 联合示例（单选）**

> 公司员工通过 HTTPS 登录内网网站。浏览器开发者工具中，可以看到登录请求的 Request Body 包含用户输入的密码。对此哪项判断最准确？

A. 在开发者工具里能看到密码，说明网络传输一定是明文。  
B. 只要登录请求使用 HTTPS，就不需要再评估密码处理、会话及日志风险。  
C. 开发者工具中可见不等于网络明文；应继续检查 TLS、服务端密码存储、日志处理和会话安全。  
D. 客户端先做一次普通 SHA-256 哈希就可以代替 HTTPS。

**正确答案：C。** A 混淆本机调试视角和网络传输；B 把传输安全误当成整体安全；D 不能替代安全传输，也不能等同于适当的密码存储策略。这类题最符合本课程目的。

## 九、综合掌握检验：五个“能做到”

学习完成后，应当能对下列**模拟场景**独立给出结构化答复：

1. **员工查询系统验收**：列出登录/数据权限/加密/日志/性能/部署/备份方面应核查的问题，能澄清“请求体可见密码”与真正网络明文传输的区别。
2. **ERP 同步接口失败**：外部请求超时，无法确定是否已成功；能解释为什么不能盲目重试，以及需要何种幂等、查询或对账方式。
3. **AI 技术选型审查**：对于几十名内部用户的普通查询服务，能够质疑没有证据的复杂微服务、缓存、消息队列堆叠，也能识别过度简化方案的安全与维护风险。
4. **AI 改动审核**：当 AI 宣称“已经完成”，能要求改动范围、测试范围、依赖变化、失败路径、密钥检查和回滚证据。
5. **系统上线交接**：能用有限时间向技术人员/AI 追问运行位置、访问边界、环境配置、备份恢复、日志监控与交接责任。

检验应考察**判断依据**而非单纯得分。题库可以支持错题回顾与复习，但记忆算法、界面呈现、数据存储等属于 App 设计，由 Codex 另行确定。

## 十、课程内容编写的验收条件

对每一章内容审查：

- [ ] 符合本章“学习内容”和“掌握标准”，深度与优先级合理。
- [ ] 从用户熟悉的企业项目场景出发，不重复讲授其已熟练的业务管理知识。
- [ ] 讲清正常路径、失败路径及为什么要关心这项知识。
- [ ] 提供至少一条可用于 AI 开发评审的具体提问。
- [ ] 给出重要概念的适用边界、误区或非目标。
